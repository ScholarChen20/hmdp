# 美食点评项目待优化功能清单

> 文档性质：项目生产化与工程能力优化计划
>
> 当前状态：以下功能均作为待优化项记录，尚未视为已经完成
>
> 优先级说明：P0 为稳定性和数据安全问题，P1 为核心能力完善，P2 为工程化、AI 安全和测试体系建设

## 一、整体目标

在现有 Spring Boot、MySQL、MyBatis-Plus、Redis、RabbitMQ、Redisson 和 Qwen 智能客服基础上，补齐以下能力：

- 保证秒杀订单消息可靠投递、重复消费可控、库存最终一致。
- 降低缓存雪崩、多级缓存不一致和缓存更新失败风险。
- 完善预约状态流转和重要写接口幂等能力。
- 提升商家搜索、智能客服和业务降级能力。
- 建立链路追踪、业务监控、日志审计和测试体系。

## 二、当前已知基础能力

以下内容属于现有项目已有基础，不代表相关优化已经全部完成：

- 商家详情使用 Redis Cache Aside 缓存。
- 商家不存在时缓存空值，具备基础缓存穿透防护。
- 秒杀使用 Redis Lua 脚本预扣库存和校验一人一单。
- RabbitMQ 已用于异步创建秒杀订单，但可靠性兜底不完整。
- 订单落库使用数据库库存条件更新。
- 预约已有创建、查询、用户取消和部分幂等逻辑。
- 智能客服已接入 Qwen、Redis 会话记忆和 Function Calling。
- 已有少量 AI 服务单元测试和基础 Redis 测试。

## 三、P0：秒杀与消息可靠性

> 目标：优先解决订单丢失、库存不一致、重复下单和消息重复投递问题。

### P0-1 RabbitMQ 增加重试队列和死信队列

- 状态：`[ ] 待优化`
- 问题：当前只有一个秒杀订单队列，消费失败后没有完整的重试和死信处理链路。
- 目标：让临时性故障可以自动重试，持续失败的消息进入死信队列，避免订单消息静默丢失。
- 方案：
  - 创建秒杀订单 Exchange 和主队列。
  - 创建延迟重试队列，例如 5 秒、30 秒两级重试队列。
  - 创建死信 Exchange 和死信队列。
  - 通过消息头记录重试次数。
  - 超过最大重试次数后进入死信队列。
- 验收标准：
  - 消费者临时异常时消息进入重试流程。
  - 超过最大重试次数的消息能够在死信队列中查询到。
  - 主队列、重试队列和死信队列均为持久化队列。

### P0-2 消费失败不能吞异常

- 状态：`[ ] 待优化`
- 问题：当前消费者捕获异常后只打印日志并结束方法，可能导致 RabbitMQ 将消息视为消费成功，造成消息丢失。
- 目标：根据异常类型决定确认、重试或进入死信队列。
- 方案：
  - 业务处理成功后才 ACK。
  - 临时异常重新投递或转发到重试队列。
  - 参数错误、数据不存在等不可恢复异常记录原因后进入死信队列。
  - 统一记录订单 ID、用户 ID、优惠券 ID 和 traceId。
- 验收标准：
  - 消费失败不会被静默确认。
  - 重试次数可控。
  - 死信消息包含原始订单信息和失败原因。

### P0-3 增加 RabbitMQ Publisher Confirm 和 Return

- 状态：`[ ] 待优化`
- 问题：当前发送秒杀消息后没有可靠确认，无法及时发现 Exchange 未确认或消息无法路由。
- 目标：确认消息是否到达 Exchange 和 Queue，并对发送失败进行补偿。
- 方案：
  - 开启 Publisher Confirm。
  - 开启 Publisher Return 和 mandatory 配置。
  - 为订单消息设置 correlationId，建议使用订单 ID。
  - 发送失败记录消息补偿记录并进行重试。
- 验收标准：
  - Exchange 确认失败可以被日志和监控捕获。
  - 无法路由的消息可以被识别。
  - 发送失败不会直接丢失 Redis 预扣库存。

### P0-4 消除 Redis Stream 与 RabbitMQ 双通道重复投递

- 状态：`[ ] 待优化`
- 问题：秒杀 Lua 脚本中写入 Redis Stream，同时 Java 入口又发送 RabbitMQ，存在同一订单被两条链路处理的风险。
- 目标：明确唯一的订单消息主链路。
- 方案：
  - RabbitMQ 作为当前秒杀订单的唯一生产和消费链路。
  - Lua 只负责库存预扣、购买资格校验和预扣记录，不再写 Redis Stream。
  - 旧 Redis Stream 代码保留前需要明确是否下线，避免误启动。
- 验收标准：
  - 同一个秒杀请求只产生一条有效订单消息。
  - 不存在 RabbitMQ 和 Redis Stream 同时消费同一订单的情况。
  - 旧代码不会在应用启动时偷偷启动消费线程。

### P0-5 增加秒杀订单数据库唯一索引

- 状态：`[ ] 待优化`
- 问题：订单表当前主要依赖 Java 查询判断一人一单，数据库层缺少 `(user_id, voucher_id)` 唯一约束。
- 目标：让数据库成为重复下单的最终兜底。
- 方案：

```sql
ALTER TABLE tb_voucher_order
ADD UNIQUE KEY uk_user_voucher (user_id, voucher_id);
```

- 验收标准：
  - 同一用户对同一优惠券只能成功插入一条订单。
  - 重复消息消费不会产生重复订单。
  - 已有脏数据时，先完成数据清理和唯一索引上线检查。

### P0-6 增加 Redis 预扣库存记录

- 状态：`[ ] 待优化`
- 问题：Lua 脚本扣减 Redis 库存后，当前缺少订单级预扣状态记录，无法判断哪些库存需要确认或回补。
- 目标：为每次预扣建立可追踪的订单预留记录。
- 建议 Key：

```text
seckill:reservation:{orderId}
seckill:reservation:timeout
```

- 记录内容：
  - 订单 ID。
  - 用户 ID。
  - 优惠券 ID。
  - 预扣时间和过期时间。
  - 状态：`PENDING`、`CONFIRMED`、`COMPENSATED`。
- 验收标准：
  - Lua 预扣成功后能够查询到对应记录。
  - 订单成功落库后状态变为 `CONFIRMED`。
  - 预扣记录具备 TTL，避免永久占用 Redis。

### P0-7 增加库存回补机制

- 状态：`[ ] 待优化`
- 问题：订单消息发送失败、消费失败或订单落库失败时，Redis 预扣库存没有回补。
- 目标：确保失败订单最终释放库存和购买资格。
- 方案：
  - 使用 Lua 脚本原子完成回补库存、删除用户购买资格和更新预扣状态。
  - 通过状态判断保证同一订单只能回补一次。
  - 消费失败进入补偿流程，不能直接重复增加库存。
- 验收标准：
  - 失败订单能够恢复 Redis 库存。
  - 回补操作重复执行不会重复增加库存。
  - 回补后用户可以重新参与秒杀。

### P0-8 增加预扣超时扫描

- 状态：`[ ] 待优化`
- 问题：消息长时间未消费或订单落库失败时，预扣库存可能永久处于占用状态。
- 目标：自动发现超时未确认的预扣记录并执行补偿。
- 方案：
  - 使用 Redis Sorted Set 按过期时间保存订单 ID。
  - 定时任务扫描已过期的预扣记录。
  - 查询订单是否已经成功落库。
  - 未落库则执行库存回补并标记为 `COMPENSATED`。
  - 使用分布式锁或 Lua 防止消费线程和补偿线程并发处理同一订单。
- 验收标准：
  - 超时订单最终能够被发现。
  - 已成功订单不会被错误回补。
  - 补偿任务支持重启后继续处理。

## 四、P1：缓存、搜索与预约核心能力

### P1-1 缓存 TTL 增加随机值

- 状态：`[ ] 待优化`
- 问题：商家缓存 TTL 固定，可能造成大量 Key 同时过期，引发缓存雪崩。
- 目标：打散缓存过期时间。
- 方案：
  - 配置基础 TTL 和随机 TTL 范围。
  - 最终 TTL = 基础 TTL + 随机值。
  - 空值缓存也可以增加小范围随机 TTL。
- 验收标准：
  - 同一批写入的商家 Key 过期时间不完全相同。
  - 基础 TTL 和随机范围可通过配置调整。
  - 缓存重建不会因固定时间集中触发。

### P1-2 引入 Caffeine 本地缓存

- 状态：`[ ] 待优化`
- 问题：当前项目没有完整的 Caffeine 本地缓存实现，多级缓存方案尚未落地。
- 目标：降低高频商家查询对 Redis 的访问压力。
- 方案：
  - 查询顺序为 Caffeine、Redis、MySQL。
  - 设置最大容量、访问过期时间和写入过期时间。
  - 更新时删除 Redis，并广播本地缓存失效。
  - 避免在本地缓存中保存过大的对象。
- 验收标准：
  - 热点商家查询能够命中 Caffeine。
  - 本地缓存满时按照策略淘汰。
  - 缓存更新后各节点不会长期保留旧数据。

### P1-3 增加本地缓存失效广播

- 状态：`[ ] 待优化`
- 问题：多实例部署时，一个实例删除自己的 Caffeine 缓存，其他实例仍可能返回旧数据。
- 目标：让所有实例都能收到缓存失效通知。
- 方案：
  - 更新数据库成功后发布商家缓存失效事件。
  - 各实例消费事件并清理本地 Caffeine。
  - 可以选择 RabbitMQ、Redis Stream 或 Redis Pub/Sub。
  - 如果使用 Pub/Sub，需要配合定时校正，因为订阅者宕机期间可能丢消息。
- 验收标准：
  - 任意实例修改商家后，其他实例的本地缓存能够失效。
  - 重复失效事件不会报错。
  - 广播失败能够被监控和补偿。

### P1-4 完善缓存一致性策略

- 状态：`[ ] 待优化`
- 目标：降低数据库与 Redis、本地缓存之间的不一致窗口。
- 方案：
  - 普通场景使用“更新数据库后删除缓存”。
  - 并发读写较多时增加延迟双删。
  - 多实例、多级缓存使用消息通知同步失效。
  - 多个数据入口修改同一张表时评估 Canal 或 Debezium Binlog 订阅。
  - 删除失败通过重试、补偿任务或可靠消息处理。
- 验收标准：
  - 缓存更新失败可以被发现。
  - 关键缓存 Key 支持手动或定时校正。
  - 文档明确不同业务场景的缓存一致性级别。

### P1-5 商家搜索升级 Elasticsearch

- 状态：`[ ] 待优化`
- 问题：当前商家名称查询依赖 MySQL `LIKE`，复杂搜索和数据量增长后扩展性有限。
- 目标：支持分词、相关性排序、拼音或多条件搜索。
- 方案：
  - 设计商家索引 Mapping。
  - 全量同步 MySQL 商家数据到 Elasticsearch。
  - 商家新增、修改、删除时同步索引。
  - ES 不可用时降级到 MySQL 查询。
  - 使用定时任务校验 MySQL 和 ES 数据差异。
- 验收标准：
  - 商家名称、商圈和地址搜索结果符合预期。
  - 索引同步失败可重试和补偿。
  - ES 故障时核心查询仍有可用降级路径。

> 如果当前商家数据量较小，可以先保留 MySQL 查询，完成搜索需求评估后再接入 Elasticsearch，避免引入不必要的基础设施复杂度。

### P1-6 完善预约状态流转

- 状态：`[ ] 待优化`
- 问题：当前预约已有创建和用户取消，但缺少确认、完成、拒绝和超时等状态流转。
- 目标：建立清晰、不可逆乱跳的预约状态机。
- 建议状态：

```text
0：待确认
1：已确认
2：用户取消
3：已完成
4：商家拒绝
5：已超时
```

- 建议流转：

```text
待确认 → 已确认
待确认 → 用户取消
待确认 → 商家拒绝
待确认 → 已超时
已确认 → 已完成
已确认 → 用户取消
```

- 验收标准：
  - 已完成、已取消和已拒绝的预约不能重复操作。
  - 每次状态变更都校验当前状态和操作人权限。
  - 状态变更有操作日志。

### P1-7 完善重要写接口幂等

- 状态：`[ ] 待优化`
- 问题：预约已有部分幂等，秒杀订单主要依赖业务查询，其他重要写接口缺少统一幂等机制。
- 目标：防止网络重试、前端重复点击和消息重复消费产生重复业务结果。
- 方案：
  - HTTP 写接口支持 Idempotency-Key。
  - 数据库建立业务唯一索引。
  - MQ 消费者以订单 ID 或业务 ID 做幂等判断。
  - 使用业务状态机限制重复状态变更。
  - 对幂等结果进行缓存，重复请求返回第一次处理结果。
- 优先覆盖：
  - 秒杀下单。
  - 到家预约创建。
  - 预约状态变更。
  - 关注、点赞和取消点赞。
  - 文件上传或其他可能重复提交的写操作。
- 验收标准：
  - 同一个幂等 Key 重复请求不会创建多条业务数据。
  - 重复 MQ 消息不会重复扣库存或创建订单。
  - 幂等失败原因和原始结果可追踪。

## 五、P2：智能客服安全、监控与测试

### P2-1 智能客服增加限流

- 状态：`[ ] 待优化`
- 问题：当前 AI 聊天接口缺少单用户、单 IP 和全局调用限制，可能造成模型费用、线程和连接资源被耗尽。
- 目标：保护模型服务和应用自身资源。
- 方案：
  - 使用 Redis 滑动窗口或令牌桶限流。
  - 设置单用户每分钟调用次数。
  - 设置单 IP 每分钟调用次数。
  - 设置全局并发数和单消息最大长度。
  - 会话上下文设置最大消息数。
- 建议 Key：

```text
ai:rate:user:{userId}:{minute}
ai:rate:ip:{ip}:{minute}
```

- 验收标准：
  - 超过限制时返回明确提示，不调用模型。
  - 限流数据在多实例之间共享。
  - 限流命中次数可以监控。

### P2-2 增加敏感词和提示词注入过滤

- 状态：`[ ] 待优化`
- 问题：当前智能客服缺少输入输出安全过滤，存在敏感内容、Prompt Injection、隐私泄露和越权指令风险。
- 目标：限制不合规内容和不安全业务意图。
- 方案：
  - 模型调用前检查用户输入。
  - 模型响应返回前检查输出内容。
  - 对手机号、地址等敏感信息脱敏。
  - 限制模型只能调用白名单工具。
  - 对预约、订单等写操作要求二次确认。
- 验收标准：
  - 敏感输入不会直接传给模型或被原样返回。
  - 模型不能调用未授权工具。
  - 预约等写操作仍然由后端校验用户身份和参数。

### P2-3 增加智能客服审计日志

- 状态：`[ ] 待优化`
- 问题：当前缺少完整的 AI 调用审计，出现错误回答、工具误调用或用户投诉时难以追溯。
- 目标：记录可审计但经过脱敏的 AI 调用链路。
- 建议记录：
  - 用户 ID。
  - 会话 ID。
  - 请求时间和 traceId。
  - 用户问题摘要。
  - 模型名称和调用耗时。
  - 工具名称和参数摘要。
  - 成功、失败和错误类型。
  - 最终响应摘要。
- 验收标准：
  - 手机号、地址、Token 等敏感信息不直接写入普通日志。
  - 可以根据用户 ID、会话 ID 或 traceId 查询一次调用链路。
  - 审计日志具备保留期限和访问权限控制。

### P2-4 增加降级 FAQ

- 状态：`[ ] 待优化`
- 问题：当前 Qwen 未启用、API Key 缺失或模型超时后，主要返回异常提示，缺少基础问题降级能力。
- 目标：模型不可用时仍能回答高频固定问题。
- 方案：
  - 准备商家营业时间、优惠券规则、预约流程等 FAQ。
  - 模型调用超时或失败后，先进行 FAQ 关键词匹配。
  - FAQ 可先放在 YAML 或数据库中，后续再接入检索能力。
  - FAQ 无匹配时提示转人工或稍后重试。
- 验收标准：
  - Qwen 不可用时常见问题仍可得到有效回答。
  - FAQ 不依赖模型服务。
  - 降级次数和失败原因可监控。

### P2-5 增加链路追踪

- 状态：`[ ] 待优化`
- 问题：当前缺少统一 traceId，HTTP 请求、RabbitMQ 消息、数据库操作和 AI 调用难以串联排查。
- 目标：实现请求级和消息级链路关联。
- 方案：
  - Filter 生成或透传 traceId。
  - 使用 MDC 写入日志上下文。
  - MQ 消息中携带 traceId。
  - 消费者、补偿任务和 AI 工具调用继续透传 traceId。
  - 根据项目规模评估 Micrometer Tracing、Zipkin 或 OpenTelemetry。
- 验收标准：
  - 一个秒杀请求可以关联到订单消息和消费结果。
  - 一个 AI 请求可以关联到模型调用和工具调用。
  - 日志中能够按 traceId 查询完整链路。

### P2-6 增加业务监控指标

- 状态：`[ ] 待优化`
- 建议指标：

```text
shop_cache_hit_total
shop_cache_miss_total
seckill_success_total
```

## 七、完成标准

本优化计划全部完成至少应满足：

- 秒杀消息失败可重试，最终失败进入死信队列。
- 重复消息不会重复创建订单或扣减库存。
- Redis 预扣库存有确认、失败回补和超时补偿。
- 缓存过期时间不会集中在同一时刻。
- 多实例本地缓存能够收到失效通知。
- 预约状态只能按照合法状态机流转。
- 重要写接口具备幂等能力。
- AI 服务具备限流、敏感内容过滤、审计和 FAQ 降级。
- HTTP、MQ、补偿任务和 AI 调用可以通过 traceId 关联。
- 核心指标可监控，异常情况可以告警。
- 核心业务具备单元测试、集成测试和压测结果。
